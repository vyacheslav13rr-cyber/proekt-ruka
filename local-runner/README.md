# Локальный запуск бота (мгновенная реакция)

Эта версия бота реагирует почти мгновенно (в отличие от бота в GitHub Actions, который просыпается раз в 5 минут) — но требует, чтобы компьютер, на котором она запущена, был включён и подключён к интернету всё время, пока нужна мгновенная реакция.

## Что нужно один раз настроить

1. Установить Node.js (версия 20 или новее) — с сайта nodejs.org, как обычную программу.
2. Установить Git — с сайта git-scm.com, как обычную программу.
3. Склонировать репозиторий на компьютер (не скачать ZIP-архивом — именно клонировать, чтобы бот мог сам делать git push):
   ```
   git clone https://github.com/vyacheslav13rr-cyber/proekt-ruka.git
   cd proekt-ruka
   ```
4. Один раз войти в GitHub из терминала, чтобы `git push` работал без запроса пароля каждый раз — при первом `git push` Git сам предложит войти через браузер (Git Credential Manager), либо можно один раз ввести логин и вместо пароля — персональный токен GitHub (Settings → Developer settings → Personal access tokens).
5. Скопировать `local-runner/config.example.json` в `local-runner/config.json` и вписать туда реальные значения `botToken`, `channelId`, `ownerChatId` — те же самые, что уже добавлены в секреты GitHub (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHANNEL_ID`, `TELEGRAM_OWNER_CHAT_ID`). Этот файл никогда не попадёт в репозиторий (он в `.gitignore`) — значения остаются только на этом компьютере.

## Запуск

Из папки репозитория:

```
node local-runner/ruka-telegram-bot.mjs
```

В терминале появится «Бот РУКА запущен, жду сообщения...» — с этого момента бот реагирует на кнопки/сообщения почти мгновенно. Окно терминала нужно оставить открытым (или запустить как фоновую службу — pm2, systemd, Планировщик заданий Windows — но это уже отдельная, более сложная настройка, можно подключить позже).

Остановить — Ctrl+C в терминале.

## Важно: не запускать одновременно с ботом в GitHub Actions

Если этот локальный бот запущен, сценарий `.github/workflows/telegram-bot.yml` начнёт получать ошибки конфликта от Telegram (два «слушателя» одновременно нельзя) — они безобидны для данных, но будут спамить в логах Actions. Автозапуск по расписанию в этом сценарии выключен именно по этой причине (см. раздел «Запуск в Docker на сервере» ниже); вручную (кнопка Run workflow) его тоже лучше не запускать, пока работает этот бот.

## Запуск в Docker на сервере (если ботов несколько — под разные проекты)

Каждый проект — свой Docker-контейнер (изолированная среда выполнения), полностью независимый от контейнеров других проектов: свой процесс, свой перезапуск, друг на друга не влияют. Для этого репозитория контейнер не копирует код внутрь себя, а монтирует (подключает как том) саму папку репозитория с диска сервера — так контейнер видит и `local-runner/config.json`, и уже настроенный git с сохранённым токеном для `git push`, без каких-либо секретов внутри самого образа.

Один раз на сервере:

1. Установить Docker (docker.com) и склонировать репозиторий — как в шагах 1–3 выше.
2. Настроить git **для этой папки** (без `--global`, чтобы настройки остались внутри `.git/config` именно этого клона и были видны контейнеру через тот же том):
   ```
   git config user.name "Имя"
   git config user.email "email@example.com"
   git config credential.helper "store --file=.git-credentials"
   ```
3. Сделать один `git push` вручную из этой папки — Git спросит логин и, вместо пароля, персональный токен GitHub (Settings → Developer settings → Personal access tokens). После этого токен сохранится в файле `.git-credentials` в корне репозитория (файл в `.gitignore`, наружу не уйдёт и в репозиторий не попадёт).
4. Скопировать `local-runner/config.example.json` в `local-runner/config.json` и заполнить `botToken`/`channelId`/`ownerChatId` — как в шаге 5 обычной установки выше.
5. Запустить контейнер:
   ```
   cd local-runner
   docker compose up -d --build
   ```

Логи — `docker compose logs -f` (из папки `local-runner`), остановить — `docker compose down`.

Если на сервере появятся боты других проектов — у каждого своя папка (свой `git clone` этого или другого репозитория) и свой `docker-compose.yml` по этому же образцу; они не пересекаются между собой.
